THEHIVE — Autonomous Campaign Blueprint

Single source of truth for every unattended firing. Not a checklist — this file IS the workflow plan, playbook, and running log, spanning as many sessions as it takes. Built 2026-08-01 after the Routine incident (see .claude/HIVE_PULSE.md and AUDIT_LEDGER.md's 2026-08-01 entries for what went wrong before). No Routine is wired to this file yet — the founder holds that step until this blueprint itself is reviewed.

This file stays small on purpose — it's what every firing reads in full. The complete, unabridged, everything-planned reference (Command Center UI plan, every domain, founder's own visionary-scope documents, all searchable by tab) lives separately in FULL_PLAN.html — open it directly for full detail on any task below; a firing only opens it if a task's Prompt explicitly says to.

Protocol — read this every firing, before anything else

  1. Caveman mode on for the whole firing (per CLAUDE.md's standing default) — terse, token-efficient, full precision, all the way through.
  2. Efficiency, concretely, not just "be terse": real per-task cost averages ~83,500 tokens (n=2 measured 2026-08-02, range 60K-107K — see Campaign Log). (a) Set a real task_budget (~150,000 tokens, generous headroom over the measured average) at the start of the firing if the harness surface supports it — lets the model see a live countdown and pace itself instead of a crude after-the-fact check. (b) Keep this file's own content (the protocol, already-done tasks) stable across firings and put anything that changes turn-to-turn last — cache-creation cost, not raw token count, was the actual driver of the original incident's expense. (c) Before starting a task that's a repeat of something done before, check workflow-optimizer's own recall step first — don't re-derive an approach that already has a recorded lesson.
  3. Find the first <div class="task" data-status="pending"> below, in document order. That is the only task under consideration. Ignore everything marked done or blocked.
  4. Read that task's Prompt and Acceptance sections. Do the work for real — run it, don't just read it.
  5. One status check per thing being watched. Never a loop. If a task involves checking CI, a PR, or a live endpoint: check it once, act on what you find, and either finish or hand off — do not re-check the same thing again in this firing hoping for a different answer. If something needs to be watched to completion, that is what subscribe_pr_activity (event-driven) is for, not a polling loop here.
  6. Before starting work, set that task's data-status="in-progress" and commit that one change by itself. If a firing ever finds a task already marked in-progress: do NOT assume it's safe to restart — check git log / open PRs for evidence of what the last firing actually did, note the finding in the Campaign Log, then decide whether to resume, redo, or mark it blocked for the founder. Never silently redo work that may already be done.
  7. When the task's Acceptance criteria are met: commit, open the PR, check CI once. NEVER merge, ever — no exceptions, not even a doc-only or test-only diff with green CI (founder-tightened 2026-08-01, overriding the old arc's prior self-merge allowance). The PR waits for the founder's own review and merge, full stop — this file's entire next test phase is specifically about proving PRs get created correctly and held for review, not about proving anything can merge unattended. Mark the task data-status="done" in this file (done means "PR ready for review," not "shipped") and append one line to the Campaign Log below (what happened, PR number, timestamp) — one line, not a narrative.
  8. Batching: if real context budget remains and the next pending task's data-batchable is true, continue to it in the same firing instead of stopping. If budget is low, or the next task is data-batchable="false" (needs a fresh, unclouded context), stop cleanly. An unreviewed PR is never a reason to stop (founder correction, 2026-08-02) — the founder reviews on their own schedule, not synchronously with each firing; waiting for review before continuing defeats the entire point of unattended work. Keep working through the queue regardless of whether earlier PRs from this or prior firings have been looked at yet, so multiple independent, reviewable PRs are waiting whenever the founder next checks — not one stalled task. Prefer one focused PR per task or coherent group of tasks over stacking everything onto a single sprawling PR — several small, reviewable PRs serve "check each one" better than one giant one.
  9. If a task is blocked on something only the founder can decide, mark it data-status="blocked", write why in its Acceptance section, and move to the next pending task rather than stalling the firing on it.
  10. Before ending the firing: verify this file was actually saved with the updated statuses and log line — the same "verify before you end the turn" discipline that the old arc's own prompt named and then failed to follow once already.
  11. If no task is left pending: stop. Do not invent new scope to fill the window — log "queue empty, nothing done" in the Campaign Log and end the firing. Only the founder adds new tasks to this file.
  12. Hard ceiling (founder-set 2026-08-01): 4 firings/day AND 3,000,000 tokens/day, whichever is hit first — now mechanically real, not a placebo. At the END of every firing, run .claude/scripts/session-usage.sh (reads this firing's own real usage straight from its Claude Code session transcript — the same source caveman-stats uses, no estimation) and append its exact TOKENS: <n> line to the Campaign Log entry for this firing. At the START of every firing, before touching any task: grep -oE 'TOKENS: [0-9]+' .claude/tasks/CAMPAIGN.html (NOT anchored to line-start with ^ — a real bug found 2026-08-02: the originally-specified anchored version found nothing at all, even a genuine entry, because it wasn't written on its own line. The unanchored form is robust to that and already verified working) for today's dated entries, sum the numbers, count today's entries. Every `TOKENS: n` occurrence must be a genuine per-firing/per-task delta (end usage minus start usage), never a running cumulative total — a separate real bug found the same day mixed the two under the same label and would have wrongly re-triggered the ceiling on a stale number. If a log entry needs to mention overall session usage for context, label it differently (e.g. "session cumulative at this point") so it's never mistaken for a summable delta. If count ≥ 4 OR token-sum ≥ 3,000,000: stop immediately, log "ceiling hit, not starting" with the actual numbers, end the firing. Still self-reported (no billing-API access from inside a firing, and the sum deliberately excludes cheap cache-read tokens — see the script's own comment) — the founder should still spot-check real spend via Settings > Usage; this ceiling is a real backstop now, not a substitute for that.
  13. Check before you build. Before writing new code for any task, grep for whether it already exists (task 11 found the "new" component library was already built, just wrong-themed and unwired — extending it took a fraction of what writing it from scratch would have). Duplicating something that already exists is a real failure mode here, not a hypothetical one.
  14. Sub-work depth — decompose, don't cram or silently expand. If working a task reveals it's actually 2+ genuinely separable pieces of work (task 2's "every tab/button", task 9's "3 gaps" are flagged examples below), split it: mark the parent task blocked with a one-line reason ("decomposed into tasks N–M"), and append the real sub-tasks as new pending entries at the end of the queue, each with its own Prompt/Acceptance. Never silently do a fraction of a big task and mark it fully done — that's exactly how things get looked over.
  15. Troubleshooting mid-task. If something breaks while doing the work (a test fails, a probe returns unexpected data, code that "should" work doesn't): apply fable-debugger's method — probe before claiming, compare against a known-working sibling, find the real coupled cause, never fake a green. Don't silently patch around it and don't silently give up — log what broke and how it was actually resolved (or why it's now blocked) in the Campaign Log, same evidence standard as everything else here.
  16. Persona — you are the Hive Organism for the duration of this task, not a generic assistant. Read .claude/agents/hive-organism.md and .claude/skills/autonomous-hive-agent/SKILL.md if not already loaded this firing. Select (and, per that file's own rule 3, only genuinely hybridize when two real concerns are named) whichever organ(s) the task needs — this is the "master developer/software engineer" method already built into this hive, not a new character to invent. If the task genuinely needs a capability no existing skill covers, skill-creator may draft one mid-firing — it is not "real" until it clears MANDATE_TRIAGE.md and ships as a normal PR, same as any other production change.
  17. Findings — capture everything noticed, even off-task. If a firing notices a bug, a real enhancement idea, or scope that was missed/never cut — anything outside the current task's own Acceptance criteria — it does NOT get silently dropped and does NOT get silently fixed off-scope either. Route it: a real bug in code you're not already touching → new entry in AUDIT_LEDGER.md's "not yet audited" list or a new pending task here if it's build-worthy; an idea/enhancement → append it as a new pending task here (marked with a one-line "founder should confirm scope" note in its Acceptance, since an idea isn't the same as an approved task); anything touching money, constitutional law, or new standing infrastructure → do not add as pending, add as blocked with the finding written out, founder decides. The point: it always lands somewhere checkable, never only in a firing's own private reasoning.
