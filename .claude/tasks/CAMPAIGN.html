THEHIVE — Autonomous Campaign Blueprint

Single source of truth for every unattended firing. Not a checklist — this file IS the workflow plan, playbook, and running log, spanning as many sessions as it takes. Built 2026-08-01 after the Routine incident (see .claude/HIVE_PULSE.md and AUDIT_LEDGER.md's 2026-08-01 entries for what went wrong before). No Routine is wired to this file yet — the founder holds that step until this blueprint itself is reviewed.

Protocol — read this every firing, before anything else

  1. Caveman mode on for the whole firing (per CLAUDE.md's standing default) — terse, token-efficient, full precision, all the way through.
  2. Find the first <div class="task" data-status="pending"> below, in document order. That is the only task under consideration. Ignore everything marked done or blocked.
  3. Read that task's Prompt and Acceptance sections. Do the work for real — run it, don't just read it.
  4. One status check per thing being watched. Never a loop. If a task involves checking CI, a PR, or a live endpoint: check it once, act on what you find, and either finish or hand off — do not re-check the same thing again in this firing hoping for a different answer. If something needs to be watched to completion, that is what subscribe_pr_activity (event-driven) is for, not a polling loop here.
  5. Before starting work, set that task's data-status="in-progress" and commit that one change by itself. If a firing ever finds a task already marked in-progress: do NOT assume it's safe to restart — check git log / open PRs for evidence of what the last firing actually did, note the finding in the Campaign Log, then decide whether to resume, redo, or mark it blocked for the founder. Never silently redo work that may already be done.
  6. When the task's Acceptance criteria are met: commit, open the PR, check CI once. Mark the task data-status="done" in this file and append one line to the Campaign Log below (what happened, PR number, timestamp) — one line, not a narrative.
  7. Batching: if real context budget remains and the next pending task's data-batchable is true, continue to it in the same firing instead of stopping. If budget is low, or the next task is data-batchable="false" (needs a fresh, unclouded context), stop cleanly.
  8. If a task is blocked on something only the founder can decide, mark it data-status="blocked", write why in its Acceptance section, and move to the next pending task rather than stalling the firing on it.
  9. Before ending the firing: verify this file was actually saved with the updated statuses and log line — the same "verify before you end the turn" discipline that the old arc's own prompt named and then failed to follow once already.
  10. If no task is left pending: stop. Do not invent new scope to fill the window — log "queue empty, nothing done" in the Campaign Log and end the firing. Only the founder adds new tasks to this file.
  11. Hard ceiling (founder-set 2026-08-01): 4 firings/day AND 3,000,000 tokens/day, whichever is hit first. Every Campaign Log entry must include this firing's own real token usage (input+output). Before starting any task, sum today's dated log entries: count of entries, and sum of their logged token counts. If count ≥ 4 OR token-sum ≥ 3,000,000: stop immediately, log "ceiling hit, not starting" with the actual numbers, end the firing. This is a self-reported estimate (no billing-API access from inside a firing) — the founder should still spot-check real spend on the Anthropic Console usage page; this ceiling is a backstop, not a substitute for that.
