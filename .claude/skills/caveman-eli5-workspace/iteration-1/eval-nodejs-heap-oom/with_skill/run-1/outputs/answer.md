Here's what's happening. When your Node app reads that 2GB CSV file the normal way, it tries to pull the whole file into memory as one giant piece before it does anything with it. Node keeps all your program's data in a space called the "heap," and that heap has a size limit. Your 2GB file is bigger than that limit, so Node runs out of room and crashes with "JavaScriptHeapOutOfMemory." That error just means "I ran out of space to hold everything you asked me to hold at once."

Streaming fixes this because it changes how the file gets read. Instead of loading the whole 2GB file into memory in one shot, streaming reads the file in small chunks, one small piece at a time, like a few kilobytes at a time. Your code processes each chunk as it arrives, does whatever it needs to do with that piece of data, and then throws that piece away before grabbing the next chunk. So at any given moment, only one small chunk is sitting in memory, not the whole file. That is why streaming stops the crash: your memory usage stays small and steady no matter how big the file is, because you're never holding more than one chunk at a time.

In Node, you'd do this with something like `fs.createReadStream()` instead of `fs.readFile()`, paired with a CSV-parsing library that supports streaming, such as `csv-parser` or `fast-csv`. Those let you handle the file row by row as it streams in, instead of waiting for the entire file to load first.
