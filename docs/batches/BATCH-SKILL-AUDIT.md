# BATCH-SKILL-AUDIT — Whole-Hive skill audit: persona + capability (founder direction 2026-11-06)

## 1. Header

- **Source:** Founder direction, 2026-11-06 chat — recorded in `docs/FOUNDERS_VISION.md` § "Skills, personas, and the absorption of capability" (commit `90612a3`, main tip after push).
- **Doctrine (verbatim from the vision addition):** A skill is not just a skill. Limiting a skill to just a skill does not give it its true capabilities, and it gives it no persona that extrapolates those capabilities and skills. Every skill carries the persona that knows when and how to use it — and a persona is itself a skill and a capability. Capabilities can extrapolate through multiple personas, and personas need necessarily certain skills. The frontend/UI is to absorb the same capabilities the operator uses through the browser web — exact where possible, reverse-engineered and adapted where not. The system optimizes utility in problematic situation awareness, formulating beyond the exoteric and the esoteric, not hindered by bias beliefs, building upon all that history and humanity has left behind, to serve as a capsule for it.
- **Scope:** All 453 `SKILL.md` files in the repo (counted 2026-11-06 at main tip `dd7fe93` via `git ls-tree`; **85 under `.claude/skills/`** — corrected from 82 by the pilot, verified by the coordinator with the same count), the rest elsewhere, mostly the skills library). Audited in slices of 10, `.claude/skills/` first (the live set), then the rest.
- **Nature:** READ-ONLY audit. It builds nothing, changes no skill, touches no code, writes nothing to the repo. Findings are recorded in the workspace; any adoption (rewriting a skill, adding a persona, merging duplicates) is a separate founder decision per item — like the Jasper 42-item review.
- **Rule:** This audit does not violate "nothing gets built until the Queen is 100%" — it builds nothing. It runs alongside the Queen sequence, not ahead of it.

## 2. Audit protocol (per skill — the standard Mac set)

For each `SKILL.md`, record one evidence row (SA-E###) with:

1. **Persona** — the named persona the skill carries, if any (name + what it is); or ABSENT (no persona — the skill is just a skill).
2. **Claimed capabilities** — what the SKILL.md says it can do (tools, commands, scripts, gates).
3. **Verified capabilities** — do the tools/commands/scripts it names actually exist in the repo at the cited paths? Checked, not assumed. Name anything claimed but missing.
4. **Cross-persona extrapolation** — which capabilities can this skill's persona carry into other personas' work; and which skills does this persona need in order to do its job (its necessary skills).
5. **Verdict** — one of:
   - `PERSONA+SKILL` — whole: persona + real capabilities, as the doctrine requires.
   - `SKILL-ONLY` — capabilities without a persona; the skill is limited to just a skill.
   - `PERSONA-ONLY` — a persona with no real capability behind it.
   - `STALE/BROKEN` — claims tools, paths, or powers that do not exist.
   - `DUPLICATE/OVERLAP` — substantially the same skill as another (name the other).
6. **Gap / recommendation** — what would make it whole (add persona X, merge with Y, correct claim Z, retire). Recommendation only — Mac decides.

**Protocol fixes applied after the pilot (2026-11-06, pilot SA-E01–SA-E10):**

- **Persona defined precisely:** a persona is a NAMED, CHARACTERIZED stance ("The Conductor — the reins-holder"). A function label ("Skill Creator") or a framing metaphor ("the organism") does not count.
- **Capability type:** record EXECUTABLE (a script, route, or file set that runs) vs PROCEDURAL (a method in prose, admitted unenforced) vs HYBRID. A verified script and a verified paragraph must not score the same.
- **Stale-binding qualifier:** a skill can be real in the repo but bound to a different environment's tools (Claude Code CLI, old trigger API). Flag `STALE-BINDING` alongside any verdict when that applies.
- **`stale_refs` field:** a whole skill can still have stale references (cited skill/route that does not exist). Record them in a standard field so they are countable across the audit.
- **Check method:** use `git ls-tree` (repo truth), not just `ls` (sparse-checkout truth), for anything outside the checked-out paths.
