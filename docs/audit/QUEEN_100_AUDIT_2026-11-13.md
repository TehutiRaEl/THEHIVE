## 4. THE GAP — "reads at 100%" vs "IS 100%"

The gap has a precise shape. It is the difference between **five things that look like completion** and **the living functions they stand in for**:

1. **"BUILT" on a status endpoint vs built in the world.** `/v11/nanuet/autonomy` says stages 1–3 are BUILT. That is a *code* claim: the functions exist, the tests pass (370/370), the deploy landed. What it does not say — and what a reader mistakes it for — is that anything has ever *happened*: no directive routed, no review logged, no memory written. A stage that has never fired is a rehearsed Queen, not a reigning one. **The fix is QB-8 and the Q-C live proofs: only real events count.**

2. **Provisioned vs inhabited.** The brain is provisioned, bound, schema-applied, and empty. Provisioning is plumbing; inhabitation is memory. Every downstream claim ("she remembers", "she learned", "she governs from experience") silently assumes the second while only the first is true. **The fix is writes: stage 1 enabled, QB-8's first row, then the Digest writing learned wisdom back — D3 + D8.**

3. **Muse knows it vs the Hive knows it.** The founder's decisions, the charter, the permissions, the amendment process, the venture manifest — all of these are in Muse's context in every turn, so in conversation it *looks* like the Hive knows them. The live Hive knows none of them (0 references, 0 routes, 0 rows). This is the recurring failure class the availability audit named: file-first, wiring-second, with "written and merged" treated as done instead of "wired and verified-live". **The fix is the absorption mechanism, Tier 0–6, with a live probe at every tier — D4–D7, D-I.**

4. **Wired vs awake.** The vision *is* wired (`queenReview()` fetches it) — but only inside the auto-approve path, which is OFF by founder decision. So the one piece of founder knowledge the Hive can read is the one piece it is forbidden to use right now. That is not a contradiction to be "fixed" by enabling switch 9; it is a design gap: the vision needs a lawful, non-auto-approve read path (or a staged proof) so she can *consult* the vision without *deciding* from it. **The fix belongs to the absorption build's design, with founder approval — D-E.**

5. **A protocol vs a runtime; a function vs an exercised path.** The Queen Digest is a document (`docs/QUEEN_DIGEST.md`); the veto is a function (`elderCouncilVeto()`, :2721). Neither has ever run. The batch plans are explicit that neither counts until it runs on real work through the real code path — and both are now *required* for 100% by this audit's definition (D8, D9), because a Queen who cannot learn from completed work and whose Council veto has never been tested is a Queen whose two closing mechanisms are hypothetical. **The fix is to build the Digest and stage the veto proof — E1, E2.**

Underneath all five sits a sixth, structural gap: **live cannot be proven to be main** (F2). Every "verified-live" claim in this audit rests on content matching (the live stage-3 text matches the merged code) rather than on deploy identity. Until a live SHA exists, the 100% claim itself is built on an unprovable deployment — BATCH-QZ QZ-5 must record that as a gap, not pass over it.

And one live hazard sits inside the gap: **the switch-9 truthiness bug** (E3). While switch 9 is OFF *by absence* of the variable, the Queen is safe. The moment anyone sets the variable to the string `"off"` in the dashboard — the natural thing to write — auto-approve silently enables. The bug must be fixed before switch 9 is ever touched, and its existence means the "switches OFF" state, though verified live today, is fragile rather than proven fail-closed.

**What "reads at 100%" would look like, and why it must not be mistaken for 100%:** stages 1–3 BUILT, brain provisioned:true bound:true, all switches OFF, PRs merged, suite green. All of that is true today, and it is worth exactly this: a foundation that has passed its own construction checks. It is not a Queen. A Queen at 100% is a Queen who has routed a real directive, logged a real review, remembered a real lesson, digested real completed work, governed a real queue, survived a real veto test, and can show the founder — live, with rows and routes — that she knows his decisions, his vision, and his law, and acts inside them.
